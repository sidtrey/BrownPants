# BrownPants Idea Queue

Ideas are kept in the order received. The current active implementation remains in its Spec Kit feature artifacts; adding an idea here does not interrupt it.

## Queue

1. **Instruction-context framing — implemented in feature 019** — Map recognized and custom instruction files, create cited response frames, detect changed sources, and explain that host configuration determines context savings.
2. **Constitution vs. spec guidance — implemented in feature 020** — Recommend constitution, feature spec, or agent guidance from explicit scope, durability, and purpose inputs; flag conflicts and suggest splitting mixed rules. The `placement` CLI keeps this rubric deterministic and engine-neutral.
3. **Acceptance-criteria integrity — next; initial gate added** — Keep acceptance criteria fixed and verifiable throughout a task so an LLM cannot quietly move the goalposts. Feature 019 now has a SHA-256 baseline, verifier, CI check, and Spec Kit before/after guidance. Explore stronger task-level enforcement and reviewed baseline updates.
4. **Lazy-load relevant context** — Explore how agents can avoid repeatedly loading every instruction file when only a few details matter. Map host capabilities, retrieval behavior, and whether BrownPants can help select and load only relevant source sections while preserving access to the complete canonical guidance.
5. **Why can’t LLMs lazy-load context?** — Explore why prompt payload size affects cost when models often use only a small portion of the supplied context. Could systems load relevant instructions or source sections on demand, while still allowing the model to find what it needs? Consider current model/API limits and whether BrownPants could help.
6. **SDD quality of life and GUI/IDE access** — Keep BrownPants' primary focus on brownfield understanding, while adding practical SDD improvements that save users hassle and prevent common workflow problems. Make the user experience welcoming to non-developers and developers, with Visual Studio and VS Code treated as first-class environments. Explore integrations for Copilot, Codex, Claude, and other GUI-based assistants, including organizations that restrict AI CLI or SDK use. Carry the product promise: “Looks like someone has the Right idea” — using BrownPants should make SDD feel easier and more dependable.
7. **Vanilla SDD vs. BrownPants comparison on a real project** — Design a repeatable, fair comparison of a baseline SDD workflow and the same workflow using BrownPants on a real codebase, potentially BrownPants itself. Measure evidence discovery, task/spec alignment, missed constraints, rework, and user effort; preserve the original task and acceptance criteria so the comparison does not move the goalposts. Introduce the same controlled bug in each condition and compare detection, diagnosis, fix quality, and regression coverage.
8. **Bridge SDD with Agile and Azure DevOps** — Explore how BrownPants can reduce the friction teams report when applying Spec Kit or other SDD engines within sprint-based delivery. Prioritize Azure DevOps: connect specs, tasks, acceptance evidence, and review status with work items and sprint workflows while keeping the team's existing planning system authoritative. Automatically reference related builds, pull requests, and releases so QA and developers can follow the evidence and shipped change without hand-copying links. Explore a “mock PR” that prepares a review-ready summary and links as a draft artifact while leaving actual PR creation and approval to a human. Start with an opt-in, reviewable integration and avoid assuming that every team uses the same Agile process.

9. **Security-conscious flow-charting** — Explore a local, text-first way to create and review diagrams for SDD work, such as flowcharts that render in terminals or Markdown and avoid external web services. Compare ASCII/text and safe image/vector export options with the draw.io workflows teams use today; prioritize no network access and clear data handling.
10. **Semantic call-resolution coverage and clarity** — Make the distinction between syntax-only invocation inventory and `--semantic` target resolution obvious to users. Review how legacy project load issues, unresolved calls, and incomplete MSBuild configurations are presented, and identify concrete ways to improve useful call tracing without overstating what was resolved.
11. **Call-trace change impact for QA and implementation decisions** — Use call relationships and repository evidence to show QA which modules and tests may be affected by a changed method or component, and help developers or agents judge impact radius and implementation complexity. Keep affected paths, callers/callees, test candidates, and confidence limits visible; do not present estimates as proven coverage or deterministic effort forecasts.
12. **README head-to-head demo and plain-English summary (after the feature queue)** — Once the planned features are implemented and reviewed, build a fair vanilla-SDD versus BrownPants comparison on a real project, include the same controlled bug in both workflows, and add the demo to the README. Make the acceptance-criteria integrity feature visible in the comparison and explain plainly how its hash detects criteria changes while work is underway. Directly below the logo, explain BrownPants in plain English for non-developers.
