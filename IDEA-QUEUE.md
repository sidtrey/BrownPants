# BrownPants Idea Queue

Ideas are kept in the order received. The current active implementation remains in its Spec Kit feature artifacts; adding an idea here does not interrupt it.

## Queue

1. **Instruction-context framing — implemented in feature 019** — Map recognized and custom instruction files, create cited response frames, detect changed sources, and explain that host configuration determines context savings.
2. **Constitution vs. spec guidance — implemented in feature 020** — Recommend constitution, feature spec, or agent guidance from explicit scope, durability, and purpose inputs; flag conflicts and suggest splitting mixed rules. The `placement` CLI keeps this rubric deterministic and engine-neutral.
3. **Acceptance-criteria integrity — implemented in feature 021** — Keep acceptance criteria fixed and verifiable throughout a task so an LLM cannot quietly move the goalposts. SHA-256 baselines, task-to-criteria evidence ledgers, reviewed rebaseline records and PR labels, CI checks, and Spec Kit before/after guidance enforce the workflow. Focused evidence, review, workflow, hash, and ledger checks pass.
4. **Lazy-load relevant context — implemented in feature 024** — BrownPants now retrieves a user-selected canonical instruction section by source and anchor, with stable Markdown/JSON output, source and line identity, fenced-code-aware heading indexes, and path/encoding/size safety. Guidance is synchronized across README and Spec Kit surfaces. Hosts must invoke retrieval and may still preload every instruction file; BrownPants makes no token-savings guarantee.
5. **Why can’t LLMs lazy-load context? — research completed** — A model can only reason over content included in its request; agent hosts can search/index locally and add selected results on demand. Retrieved text still counts as model input. Prompt caching can reduce the price of repeated prefixes on supported APIs, but cached tokens remain processed input and count toward context/rate limits. Hosts differ: for example, Claude Code loads parent `CLAUDE.md` files at launch while nested rules can load on demand. BrownPants can provide deterministic section discovery/retrieval, provenance, and size/token estimates; the host must invoke it, and estimates must not be presented as provider usage. Sources: [VS Code context](https://code.visualstudio.com/docs/agents/concepts/context), [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching), [Claude Code memory](https://code.claude.com/docs/en/memory), [Claude prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).
6. **SDD quality of life and GUI/IDE access** — In progress in feature 026: add a user-invoked GitHub Copilot context prompt for Visual Studio and VS Code Local harness, with a safe local installer and fallback when agent terminal access is restricted. Keep the broader goal open: support non-developers and developers, investigate Copilot's other harnesses and Codex/Claude GUI integrations, and serve organizations that block AI-specific CLI or SDK clients. Keep brownfield understanding primary and the user experience approachable. Carry the product promise: “Looks like someone has the Right idea” — using BrownPants should make SDD feel easier and more dependable.
7. **Vanilla SDD vs. BrownPants comparison on a real project** — Design a repeatable, fair comparison of a baseline SDD workflow and the same workflow using BrownPants on a real codebase, potentially BrownPants itself. Measure evidence discovery, task/spec alignment, missed constraints, rework, user effort, and token usage; preserve the original task and acceptance criteria so the comparison does not move the goalposts. Introduce the same controlled bug in each condition and compare detection, diagnosis, fix quality, and regression coverage. Record input/output token counts for every run, identify the host and model, and distinguish provider-reported counts from estimates or unavailable usage data.
8. **Bridge SDD with Agile and Azure DevOps (in progress in feature 030)** — Reduce friction when applying Spec Kit or other SDD engines within sprint-based delivery. Prioritize Azure DevOps Boards and Azure Repos Git: connect specs, tasks, acceptance evidence, and review status with work items and sprint workflows while keeping the team's existing planning system authoritative. Automatically reference related builds, pull requests, and releases so QA and developers can follow evidence and shipped changes without hand-copying links. Prepare a local PR preview, then allow explicit creation of a draft Azure Repos PR with mapped work items; leave review, approval, merge, and completion to humans. Keep the integration opt-in and reviewable; do not assume every team uses the same Agile process.

9. **Security-conscious flow-charting** — Explore a local, text-first way to create and review diagrams for SDD work, such as flowcharts that render in terminals or Markdown and avoid external web services. Compare ASCII/text and safe image/vector export options with the draw.io workflows teams use today; prioritize no network access and clear data handling.
10. **Semantic call-resolution coverage and clarity** — Make the distinction between syntax-only invocation inventory and `--semantic` target resolution obvious to users. Review how legacy project load issues, unresolved calls, and incomplete MSBuild configurations are presented, and identify concrete ways to improve useful call tracing without overstating what was resolved.
11. **Call-trace change impact for QA and implementation decisions** — Use call relationships and repository evidence to show QA which modules and tests may be affected by a changed method or component, and help developers or agents judge impact radius and implementation complexity. Keep affected paths, callers/callees, test candidates, and confidence limits visible; do not present estimates as proven coverage or deterministic effort forecasts.
12. **README head-to-head demo and plain-English summary (after the feature queue)** — Once the planned features are implemented and reviewed, build a fair vanilla-SDD versus BrownPants comparison on a real project, include the same controlled bug in both workflows, and add the demo to the README. Report input/output token counts per run with model, host, and measurement-source details; mark estimates and unavailable counts clearly. Make the acceptance-criteria integrity feature visible in the comparison and explain plainly how its hash detects criteria changes while work is underway. Directly below the logo, explain BrownPants in plain English for non-developers.
13. **Model selection by task and SDD phase** — Explore how teams can assign model choices by task type or workflow phase: reserve stronger models for code changes and use lower-cost models for routine drafting, summaries, or checks when quality allows. Compare what Claude, VS Code/Copilot, Codex, and other hosts expose, distinguish portable SDD guidance from host-enforced selection, and make cost/quality tradeoffs reviewable without pretending unsupported hosts honor the choice.
14. **Human-controlled pull request creation across providers** — Extend the Azure Repos Git draft-PR workflow from feature 030 to other providers teams use, with linked specs, tasks, acceptance evidence, builds, and releases where supported. Keep approval, merge, and completion under human control; BrownPants must never approve its own PR or merge/complete it. Make the draft summary and proposed links reviewable before creation, with clear opt-in behavior and the narrowest provider permissions available.
15. **WinForms cross-thread UI access analysis** — Help teams find Windows Forms `Control` property assignments that may execute from a non-UI thread, a difficult class of brownfield bugs. Trace the assignment target and surrounding execution path where supported; recognize marshaling patterns such as `InvokeRequired`, `Invoke`/`BeginInvoke`, and `SynchronizationContext`. Clearly label syntax-only matches as candidates, show source locations and confidence limits, and do not claim a thread-safety defect from a `Control` property set alone.

16. **QA knowledge transfer across the sprint lifecycle** — Reflect teams where a story links work from all roles (analysis, code, tests, docs, PR); after review/build, help QA find the acceptance criteria, documented test steps, evidence, and deployment/release links in one handoff. Keep observed ADO links distinct from inferred ones, never invent test procedures, and show gaps. The Azure DevOps bridge should make existing story/task/PR/build/release relationships easy to follow; any authoring or state-changing workflow needs its own acceptance criteria and review.
